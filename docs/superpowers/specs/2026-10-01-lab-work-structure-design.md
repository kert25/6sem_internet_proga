# Миграция структуры лабораторных и развитие `lab-works`

**Дата:** 2026-10-01  
**Статус:** ожидает проверки пользователем

## Цель

Привести проект «Интернет-программирование» к переносимой структуре скилла
`lab-works`, не меняя исходники, методички или готовые документы. Устранить
дублирование двух планов, сделав `_context.json` источником постоянных данных,
`_lab_state.json` — машиночитаемым состоянием и местом подтверждённых
проектных решений, а методички — первичным источником задания.

Одновременно дополнить глобальный скилл для проектов, в которых номер
рабочего каталога не совпадает с официальным номером лабораторной.

## Источники истины

Приоритет данных:

1. Методичка, указанная в `methodical_guide`: официальные номер, тема,
   формулировка задания, требования к коду и отчёту.
2. Явно подтверждённые пользователем данные в `_context.json` и
   `_lab_state.json`: вариант, сопоставление каталогов с методичками,
   согласованные решения, фактический статус, команды и артефакты.
3. Файлы в каталоге лабораторной: исходники, данные, снимки и документы.

Имя каталога никогда не заменяет сведения из методички. Его роль — только
организация файлов в конкретном проекте.

## Целевая структура проекта

```text
ЛРN/                         # исходники и результаты одной лабораторной
  <methodical guide>.pdf      # исходное имя методички сохраняется
  screenshots/                # снимки для отчёта, если нужны
  content.json                # содержание отчёта, если отчёт собирается
  content_text.json           # содержание конспекта, если он собирается
  Отчет_ЛРN.docx
  Отчет_ЛРN.pdf
  text.docx
_libs/                        # опционально: локальные общие зависимости
_tools/make_docx.py           # вузовая адаптация сборщика, если она нужна
_context.json                 # постоянные данные титульного листа
_lab_state.json               # состояние работ и подтверждённые решения
ЛР_пример.docx                # образец титульника пользователя
```

`_libs/` предназначен для файлов, которые сознательно используются несколькими
лабораторными (например, локальных версий jQuery). Скилл не копирует такие
ресурсы в каждую ЛР без отдельной причины.

В данном проекте остаётся локальным только `_tools/make_docx.py`, потому что
он воспроизводит образец ТулГУ. Существующие локальные копии других утилит не
удаляются этой миграцией: они не мешают структуре и могут быть использованы
проектом. Для новых запусков приоритет у актуальных инструментов глобального
скилла.

## Формат `_lab_state.json`

Базовый формат скилла расширяется обратно совместимыми полями:

```json
{
  "version": 2,
  "commit_on_completion": false,
  "project_notes": [
    "Методичка — первичный источник номера, темы и задания.",
    "Рабочий каталог ЛРN может не совпадать с официальным номером работы."
  ],
  "labs": {
    "1": {
      "status": "ready_for_review",
      "directory": "ЛР1",
      "methodical_guide": "ЛР1/Лабораторная работа 9 _Основы JavaScript.pdf",
      "report_number": 9,
      "theme": "Основы JavaScript",
      "variant": null,
      "next_step": "Проверить ЛР1 и сообщить замечания либо подтвердить сдачу",
      "commands": {},
      "artifacts": [
        "ЛР1/Отчет_ЛР1.docx",
        "ЛР1/Отчет_ЛР1.pdf",
        "ЛР1/text.docx"
      ],
      "notes": []
    }
  }
}
```

### Семантика новых полей

- `directory` — относительный путь рабочего каталога. Если его нет, скилл
  использует совместимый путь `ЛР<ключ labs>`.
- `report_number` — официальный номер из методички, который передаётся в
  титульник. Если его нет, применяется ключ записи, чтобы старые состояния
  продолжали работать.
- `methodical_guide` — относительный путь к методичке с сохранённым исходным
  именем. Скилл проверяет существование пути, когда поле задано.
- `project_notes` и `notes` — только подтверждённые решения, отсутствующие в
  методичке: выбранная предметная область, особенности варианта, общие
  зависимости и ограничения окружения. Они не дублируют текст заданий.
- `shared_resources` (необязательное поле записи) — относительные ссылки на
  общие материалы; они не копируются между лабораторными.

## Состояние дисциплины «Интернет-программирование»

В миграцию войдут записи `1`–`8`:

| Ключ / каталог | Номер из методички | Тема | Статус |
|---|---:|---|---|
| `1` / `ЛР1` | 9 | Основы JavaScript | `ready_for_review` |
| `2` / `ЛР2` | 10 | Функция и обработка события на JavaScript | `not_started` |
| `3` / `ЛР3` | 11 | Организация ветвлений и работа с методами в JavaScript | `not_started` |
| `4` / `ЛР4` | 12 | XML документы | `not_started` |
| `5` / `ЛР5` | 13 | XML DTD | `not_started` |
| `6` / `ЛР6` | 14 | XML Schema | `not_started` |
| `7` / `ЛР7` | 15 | Использование языка PHP | `not_started` |
| `8` / `ЛР8` | 16 | Основы jQuery | `not_started` |

У ЛР2–ЛР8 будет указан вариант `9`. У ЛР1 вариант не применяется. Общие
решения проекта, которые должны сохраниться после удаления планов:

- вариант — номер `9` в списке группы;
- ЛР4–ЛР6 используют общую предметную область «Видеотека»;
- ЛР7 запускается встроенным сервером PHP (`php -S`), Denwer не нужен;
- ЛР8 использует локальные `_libs/jquery-3.7.1.min.js` и
  `_libs/jquery-1.12.4.min.js`;
- код сопровождается комментариями;
- для ЛР8 при номере по списку 9 применяется согласованное циклическое
  сопоставление индивидуальных заданий: `1/1`, `2/4`, `3/2`, `4/3`;
- ЛР1: все 20 заданий выполнены; особое отображение имён файлов и сценариев
  демонстрации уже находится в `ЛР1/text.docx`.

Подробные формулировки заданий намеренно не переносятся: они остаются в
методичках. Это исключает два конкурирующих источника истины.

## Удаление дублирующих планов

После создания и проверки `_lab_state.json` удалить:

- `ПЛАН_ЛАБОРАТОРНЫХ.md`;
- `ПЛАН_ДОРАБОТКИ_СКИЛЛА.md`.

Первый файл будет заменён состоянием, ссылками на методички и сохранёнными
подтверждёнными решениями. Второй не является артефактом лабораторной и
дублирует уже реализованные изменения глобального скилла. Спецификация
остается как запись об архитектурном решении и миграции.

## Изменения глобального скилла `lab-works`

### `SKILL.md`

1. В разделе о `_lab_state.json` описать поля `directory`, `report_number`,
   `shared_resources`, `project_notes` и `notes`.
2. Зафиксировать правило: методичка — первичный источник официального номера,
   темы и задания; каталог — только рабочий путь.
3. Добавить `_libs/` в структуру как необязательную папку локальных общих
   зависимостей.
4. Уточнить ASCII-safe пример: `--lab` выбирает запись состояния, а номер для
   титульника берётся из `report_number`.

### `scripts/lab_runner.py`

1. `paths_for()` использует `directory`, иначе `ЛР<номер>`.
2. `build_report()` передаёт `report_number`, иначе ключ записи, в
   `make_docx.build()`.
3. При наличии `methodical_guide` проверяется существование файла до сборки.
4. Старые состояния версии 1, где новых полей нет, сохраняют прежнее
   поведение.

### `evals/evals.json`

Добавить проверки для:

1. папки `ЛР1` и титульника с официальным номером `9`;
2. произвольного каталога из `directory`;
3. общих ресурсов нескольких лабораторных;
4. отсутствующей либо противоречащей методички, когда агент не имеет права
   угадывать номер, тему или задание по имени каталога.

## Проверка после реализации

1. Проверить JSON `_context.json` и `_lab_state.json` стандартным парсером.
2. Запустить runner для ЛР1 в режиме `verify-report`; должны быть найдены
   DOCX, PDF и `text.docx`.
3. Создать временное состояние с несовпадающими номером каталога и
   `report_number`, собрать тестовый DOCX и проверить номер в документе через
   `inspect_docx.py`.
4. Убедиться, что ЛР2–ЛР8 ссылаются на существующие методички.
5. Проверить, что удалены только два плановых Markdown-файла, а исходники,
   методички и документы не изменены.
